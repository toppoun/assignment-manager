# Notion同期 Phase 3C

Notion API `2026-03-11` の課題ページ作成と更新を、HTTPモックで検証できる。通常ビルドのCLIは従来の読み取り専用経路を使う。書き込み処理にも、合成fixture用に作られたループバックHTTPクライアントかを送信前に確認するガードがある。

```sh
cargo run --locked --offline --features synthetic-https-fixture -- fixture-apply
```

このコマンドは合成大学から10件を取得し、同じインメモリのNotionモックと一時SQLiteで2回同期する。初回は10件作成、2回目は10件変更なしになる。実データ向けの設定・資格情報と、既存の `sync --dry-run` 用状態DBから独立している。

## 書き込み条件

- 実行ロックを取得して対象専用の状態DBを検証し、スキーマ・Relation先と全ページを読み直す。途中の取得失敗、ページングの打ち切り、比較項目の欠落があれば書き込みを保留する。
- Create直前は同期キーで再検索する。0件かつ既存の状態行がない場合だけ作成意図を保存して送信する。1件が新たに現れた場合は既存ページとして対応を記録し、次回の全件取得で差分を計画する。複数件はConflict、状態DBのページIDと食い違う場合はDeferredにする。
- Createは課題名、取得元、同期キー、期限がある場合はその期限、確認済みの授業対応があればそのRelationを送る。PATCHは変更がある課題名・期限・取得元と、条件を満たす空欄Relationだけを送る。期限のクリアは `date: null` を使う。提出URL、状態、優先度、メモ、繰り返し、本文、設定済みRelationは保持する。
- PATCH前は対象ページをGETし、ID・同期キー・親データソース・ゴミ箱／アーカイブ状態・比較項目・全Relation・最終更新時刻を照合する。最終更新時刻は競合検出にだけ使う。
- タイトルと期限が完全一致する手動課題が見つかった場合は `manual_candidates` に計上し、対応するCreateを保留する。タイトル・期限だけでは同一課題と判定できない。明示的なページIDによる紐づけは、対象・権限・キー・所有権を別途確認する手順が必要なため、今回のCLIには設けていない。

ページの作成先、プロパティID指定、更新の形式はNotionの公式リファレンスに従う。 [Create a page](https://developers.notion.com/reference/post-page) · [Update page](https://developers.notion.com/reference/patch-page) · [Retrieve a page](https://developers.notion.com/reference/retrieve-a-page)

## 障害からの復旧

| 障害・観測結果 | 同期時の動作と復旧方法 |
| --- | --- |
| POSTのタイムアウト・接続断・不正な成功応答・529・5xx | 作成意図を `unknown` にし、pendingとして保持する。後続実行で全件取得から照合する。結果不明のPOSTは自動再送しない。 |
| POST直前・直後にプロセス終了、またはNotionで作成成功後にSQLiteの書き込み失敗 | コミット済みの `intent` が再送を防ぐ。SQLiteのI/O・容量・権限を復旧し、同じDBと対象で再照合する。保存エラーを受けてもNotionで未作成とは判断しない。 |
| pendingのキーが1件見つかる | ページIDの対応と親を検証して `linked` にする。候補がなくても紐づけは復旧できる。候補があれば通常の差分計画に進める。 |
| pendingのキーが0件、または取得が失敗・不完全 | 作成意図を保持してDeferredにする。Notionの権限、移動、ゴミ箱、取得範囲を確認する。0件という結果だけを根拠に意図を消したり作成したりしない。 |
| 同一キーが複数件、または状態DBとNotionのページIDが矛盾 | 重複はConflict、IDの矛盾はDeferred。履歴と現存ページを確認し、正本と扱いを人が決める。自動削除やリンク先の差し替えは行わない。 |
| PATCHの結果が不明 | 同じページを再取得し、送信した変更項目が一致する場合に反映済みとする。照合不能・不一致ならDeferred。同じPATCHは再送せず、次回は新しいスナップショットと取得結果から差分を計画する。 |
| 更新前の手動編集・Relation変更・削除・移動・アーカイブ、PATCHの404／409 | 該当項目をDeferredにする。ページや共有状態を確認する。既知の対応が消えた場合も、新規ページで置き換えない。 |
| 400・401・403などの明示的な拒否 | 設定、認証、Notionの共有・スキーマを確認する。400・401・403・404・409・429で作成が拒否された場合だけ、その回の作成意図を解除する。同じ実行で書き込みを再試行しない。解除自体に失敗した場合はpendingとして復旧する。 |
| 429／529 | `Retry-After` を後続リクエストにも適用する。60秒を超える待機は打ち切り、そのクライアントは期限まで送信を保留する。読み取りは初回を含め最大3回。実向けクライアントは送信開始を350 ms以上空ける。別プロセスに切り替える場合もサービスの待機期限を守る。 |
| 状態DB破損・取り違え | 開く際に識別子・対象・整合性を確認し、Notion通信前に中断する。DBと残っているジャーナルを保全し、復元したDBに書き込み前の作成意図が揃っていることを確認する。意図を失っている可能性がある場合は対象への書き込みを保留し、手動で作成履歴を検証する。 |
| 多重起動・誤った送信先 | 同じロックを使う並行実行を拒否する。プロセス終了でOSロックは解放される。書き込み先は固定のローカルHTTPモックに限定し、リダイレクトとプロキシを使わない。 |

HTTPエラーはステータス・固定分類のみで報告する。認証値、大学由来の生ID、機密URL、レスポンス本文は出力しない。 [Request limits](https://developers.notion.com/reference/request-limits) · [Status codes](https://developers.notion.com/reference/status-codes)

## 保証範囲と有効化前の条件

Notionには同期キーの一意制約がない。キー再検索とPOSTの間に外部プロセスが作成することや、複数ページの取得中に外部から変更されることまでは防げない。実行排他は同じロックを共有するCLIに限られる。公開PATCH仕様に `If-Match` や更新時刻を前提とした条件付き更新は記載されていない。409は個別の手動編集を必ず検出する仕組みではないため、直前GETからPATCHまでに入った手動編集や移動を完全には防げない。 [Update page](https://developers.notion.com/reference/patch-page) · [Status codes](https://developers.notion.com/reference/status-codes)

実書き込みを有効化する前に、実対象と同等の検証用データソースで別途承認を得て、APIバージョン・権限・ページ所属・プロパティ・Relationの完全性と作成／更新の疎通を確認する。実運用では、対象の明示選択、権限を絞った接続、単一の書き込み主体、状態DBと未確定意図の保全、保留・重複・手動候補の確認手順を用意する。授業Relationを使う場合は事前に対応表の一意性を確認する。提出URLは取得元で検証方法が確立するまで書き込み対象から外す。
